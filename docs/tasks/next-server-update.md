# Правки для следующего общего обновления сервера

Порядок согласован с Иданом 11.11.2026. Реализация общего выпуска
2026.11.13.1 подготовлена 13.11.2026; установка на сервер и проверка на устройствах
ещё должны быть подтверждены. Порядок установки: `docs/guides/update-20261113.md`.

- Новые задания по исправлению сервера сначала записываем сюда.
- Не начинаем выполнять и не развёртываем каждое задание отдельно.
- По команде Идана на следующий общий апдейт выполняем накопленные задания вместе,
  проверяем изменения и выпускаем одно обновление с записью в журнале версий.
- Если формулировка требует уточнения, сохраняем вопрос рядом с заданием.
- В этом публичном файле не храним личные данные клиентов, закрытые цены или секреты.

## Ожидают выполнения

1. **Значок программы для ярлыков.** Добавить узнаваемую иконку приложения для
   ярлыков на компьютере, телефоне и планшете Android, а также для вкладки браузера.
   Проверить, что значок используется при добавлении программы на главный экран.
2. **Итоги месяца в таблице «Месячный оборот по фирмам».** Сохранить разбивку
   по поставщикам и добавить для каждого месяца заметную строку «Итого за месяц»:
   общее количество заказов, общий оборот с НДС и средний чек по всем фирмам.
   Общий средний чек рассчитывать как общий оборот / общее количество заказов.
   Разные валюты суммировать отдельно; использовать те же правила включения заказов
   и определения месяца, что и существующая таблица.

3. **Цепи для снега — Kaizen Rent.** По сообщению Идана услуга есть в прайсе
   поставщика, но программа ошибочно сообщает об отсутствии. Проверить актуальный
   прайс, запись услуги и её сопоставление с поставщиком; исправить доступность
   и расчёт цены по данным прайса. Проверить выбор услуги и её отображение в письме
   поставщику. Выпустить на сервер вместе со следующим общим обновлением.

4. **Выравнивание отправленных оферт, включая отправку с Android.** По снимку
   вступление и часть разделов письма неожиданно центрируются, тогда как блок
   «חשוב לדעת» остаётся выровненным справа. Проверить HTML реально отправленной
   оферты и путь отправки с компьютера/телефона/планшета. В шаблоне есть внешняя
   ячейка `align="center"` и внутренний контейнер с направленным выравниванием;
   это возможный источник наследования, но причина конкретного письма ещё не доказана.
   Отделить центрирование контейнера от выравнивания текста: иврит справа (RTL),
   английский/польский/русский слева (LTR). Явно задать совместимые с почтой
   атрибуты и стили для содержательных ячеек/блоков; проверить структуру HTML,
   ширину и читабельность в Gmail на компьютере и Android. Не менять исходную
   оферту или повторно отправлять письма клиентам при проверке.

5. **Два поля имени в ручном заказе.** ManualBookingForm наследует `full_name`
   из FirstInquiryForm и дополнительно объявляет `customer_name` с тем же названием
   «Имя и фамилия». Удаляются только прежние `first_name`/`last_name`, поэтому
   шаблон выводит оба новых поля. Оставить один источник имени для ввода, вставки
   из текста и проверки обязательности; сохранить правильное заполнение снимка
   клиента и водителей. Проверить повторный показ формы после ошибки и подтверждение
   цены. По скриншоту обязательное поле остаётся с ошибкой при заполненном втором.

6. **Клонированные заказы не видны в исходной оферте.** Идан создал заказ из
   оферты, затем три раза клонировал и изменял его. В оферте показывается только
   первый заказ. Проверить сохранение связи с исходной офертой при клонировании,
   включая цепочку клонов и смену поставщика/класса. В оферте должны отображаться
   все связанные заказы с их актуальными статусами, включая отменённые, без
   повторного подсчёта самой оферты в конверсии. Для уже созданных клонов
   восстановить связь только по подтверждённому происхождению, не по одному
   совпадению имени клиента. Проверить, что независимый новый заказ не связывается
   с чужой офертой. Реализация — в следующем общем обновлении.

7. **Ручная отметка передачи изменений без отправки UPDATE.** На экране письма
   об изменении заказа добавить действие «Изменения переданы вручную / по телефону».
   Оно должно фиксировать дату, оператора и способ связи в истории, сохранять
   актуальные изменения и убирать неверную отметку «черновик, не отправлено»,
   не отправляя письмо через SMTP. Отличать передачу просьбы от уже согласованных
   с поставщиком изменений: дать возможность явно отметить подтверждение по
   телефону без обязательного ваучера. Сам факт ручной передачи не должен
   автоматически означать подтверждение поставщиком. Повторное нажатие не должно
   создавать дубликаты событий. При смене поставщика учитывать отдельные действия
   отмены у старого и нового заказа у нового, не отмечать оба выполненными одним
   неподтверждённым действием. Выполнить вместе с общим обновлением.

8. **Точное сопоставление категорий формы по таблице Идана.** Получена заполненная
   таблица 13.11.2026. Использовать только ячейки «Да»; пустые ячейки и «Нет»
   означают исключение. Всего 144 соответствия: Kaizen Rent — 50, Car Free — 24,
   One Rent — 42, MM Cars — 28. Исходная копия и извлечённые соответствия сохранены
   отдельно в закрытой папке `private_uploads/vehicle-category-mapping/20261113/`.
   Применять как явную конфигурацию в базе, без дополнительных догадок по названиям
   или включения похожих классов. Проверить каждую из 14 категорий, каждую фирму,
   отрицательные случаи и группы, отмеченные в нескольких категориях. Сами закрытые
   файлы в публичный Git не добавлять. Выполнить в общем обновлении.

## Выполнены в общем обновлении

Все восемь пунктов включены в код выпуска 2026.11.13.1. Пункт 8 активируется
после загрузки утверждённого файла владельцем на сервере. Для пункта 6 связь

копий без доказанного происхождения не выполняется.
