# Переход на сервер — состояние на 10.11.2026

Идан подтвердил завершение октябрьских сверок. Основной источник заказов до
переключения — локальная база программы. Общий рабочий файл —
`OneDrive/RentalCar/All_orders.xlsx`; отдельные таблицы по фирмам больше не ведём.
Excel обновляется по команде сверки, а не непрерывно.

Код и журнал версий сохраняются в Git. База, Excel, файлы клиентов, отчёты сверок
и секреты в публичный Git не попадают. Git не заменяет резервную копию данных.

## Что уже проверяли

- На Render работают приложение, PostgreSQL и постоянный диск.
- Есть отдельная тестовая база восстановления; она не должна заменять основную.
- Выполнялись проверка восстановления базы и отдельная проверка восстановления PDF.
- Сервер выгружает зашифрованные копии базы и вложений; проверялась обратная загрузка.
- Рабочая почта проверялась в режиме отправки только оператору.
- В программе есть обмен с общим Excel и дополнительный Excel-снимок в серверной копии.

Эти проверки относятся к предыдущему серверному состоянию. Они не означают,
что последние локальные заказы уже перенесены или что новые версии развёрнуты.

## Перед переключением

1. Развернуть сохранённую версию кода. Проверить версию и миграции на Render.
2. Проверить тариф и срок действия **основной** базы, место на диске и доступ владельца.
3. Подготовить и проверить процедуру импорта SQLite → PostgreSQL на отдельной копии.
   Она должна переносить пользователей, заказы, оферты, цены, сверки, историю,
   версии Excel и ссылки на вложения. Нельзя переносить только таблицу заказов.
4. На время окончательного экспорта прекратить запись в локальную программу.
   Сделать полную копию базы и файлов. Сохранить также текущую серверную базу.
5. Перенести данные и постоянные файлы по проверенной процедуре. Не затирать
   серверные настройки подключения, ключи и конфигурацию шифрования резервных копий.
6. Сравнить количество записей по всем переносимым таблицам, октябрьские итоги,
   новые и отменённые заказы, пользователей и контрольные суммы файлов.
7. На сервере проверить вход, создание/изменение/отмену заказа, получение вложения
   и тестовое письмо владельцу. Включение реальной рабочей почты — отдельный шаг:
   защитный режим `WORK_MAIL_MODE=test-only` пока не доказывает готовность реальной отправки.
8. Сделать резервную копию **уже перенесённых** данных и проверить её восстановление.
9. После проверки работать только на сервере. Локальную копию сохранить для возврата.
   Если после переключения на сервере появились новые заказы, нельзя просто начать
   писать в старую локальную копию: сначала нужно сохранить и вернуть новые данные.

## Общий Excel после перехода

Сервер не видит локальную папку OneDrive напрямую. Сохраняем рабочую процедуру:
закрыть Excel → загрузить актуальную книгу в «Синхронизация Excel» → проверить
различия → применить → скачать результат в ту же папку OneDrive.
Само наличие OneDrive на компьютере не настраивает серверную синхронизацию.

## Проверка полной копии перед остановкой работы

Локально (каждый раз использовать новые имена, существующие копии не заменяются):

```powershell
uv run python scripts/cutover_transfer.py export private_uploads/server-cutover/trial.zip
uv run python scripts/cutover_transfer.py local-test private_uploads/server-cutover/trial.zip private_uploads/server-cutover/trial-local
```

Пакет содержит личные данные, пароли пользователей в виде хешей, закрытые цены и вложения.
Его нельзя добавлять в Git или размещать по публичной ссылке. Сеансы браузера не переносятся.
После развёртывания нового кода владелец может загрузить пакет через `/admin/cutover-upload/`.
Сверить SHA256 с результатом экспорта. Страница только сохраняет закрытый пакет, не импортирует его.
В Render Shell выполнить показанную на странице команду `postgres-test`.
Она использует только `RESTORE_TEST_DATABASE_URL`, проверяет, что это отдельная тестовая база,
и создаёт в ней новую схему. Старые тестовые данные и основная база не заменяются.

Проверка сравнивает число и содержимое записей каждой модели, связи и вложения.
Доли секунды сохраняются полностью. Успешная локальная проверка ещё не подтверждает
совместимость с PostgreSQL: обязателен отдельный успешный запуск на Render.
Эти команды предназначены для репетиции и не переключают рабочую программу на сервер.
До окончательной остановки локальной записи пакет считается предварительным.

## Окончательный перенос после успешного испытания PostgreSQL

1. Объявить остановку локального ввода всем пользователям. Не вносить данные и на сервере.
2. Создать свежий пакет через `export` под новым именем и сохранить его SHA256.
3. Загрузить пакет владельцем через закрытую страницу; сверить SHA256.
4. Выполнить в Render Shell (подставить путь и SHA256 нового пакета):

   ```bash
   uv run python scripts/cutover_transfer.py stage-primary '/var/data/backup-private/cutover-incoming/PACKAGE.zip' --sha256 SHA256
   ```

   Команда сохраняет `pg_dump` текущей серверной базы, создаёт отдельную схему в основной базе
   и полностью проверяет восстановленные данные. Результат `staged-not-live` ещё не переключает программу.
   На сервере должно быть ноль заказов, иначе команда откажется продолжать.

5. Подставить имя схемы из результата и тот же SHA256:

   ```bash
   uv run python scripts/cutover_transfer.py activate-primary cutover_trial_SCHEMA --sha256 SHA256
   ```

   Команда повторно сверяет содержимое всех моделей, копирует вложения без замены конфликтующих файлов
   и в одной транзакции переименовывает две схемы. Старые данные остаются в `cutover_previous_...`.
   При ошибке переименования оба изменения откатываются. При появлении заказов в старой базе переключение запрещено.
6. Сразу перезапустить сервис Render, чтобы открытые подключения использовали новые таблицы.
   Повторно войти с локальными учётными данными. Проверить количество заказов, октябрьские итоги и вложения.
7. Проверить рабочую почту и резервное копирование. До этих проверок не объявлять запуск завершённым.
   Не удалять старые схемы или локальную базу. Для возврата потребуется отдельная проверка новых серверных записей;
   автоматическое переключение обратно не выполняется.

## Условие готовности

Переключение готово только после проверенного импорта, сверки данных, проверки
реальной почты и резервной копии перенесённых данных. До этого сервер подготовлен,
но актуальная рабочая база остаётся локальной.
